# API Reference

Base URL (local dev): `http://localhost:8000`. Interactive docs are also
available at `/docs` (Swagger UI, auto-generated by FastAPI) once the
backend is running.

## Chat

### `POST /chat`

Runs the full LangGraph agent loop: understand → retrieve context → identify
transaction → investigate → evaluate policy → decide → act → schedule
follow-up → audit → respond.

```json
// Request
{ "customer_id": "CUST001", "message": "Mere 2400 kat gaye but payment fail ho gaya", "case_id": null }

// Response
{
  "case_id": "CASE-1042",
  "message": "Maine aapka transaction check kiya...",
  "intent": "FAILED_PAYMENT",
  "status": "WAITING_FOR_RESOLUTION",
  "actions": ["TICKET_CREATED", "ACTION_TAKEN", "FOLLOWUP_SCHEDULED"],
  "context_used": {
    "previous_case_found": false,
    "related_transaction_found": true,
    "semantic_memory_hits": 0
  }
}
```

`context_used` is a non-sensitive summary of what context the agent drew
on (spec section 26) — never raw memory content. `semantic_memory_hits` is
0 whenever Cognee isn't configured; the rest of the response is otherwise
unaffected (see `docs/architecture.md` "Memory: Cognee").

If the customer's message contains a UPI PIN/OTP/card PIN/password, the
response is a security warning and `case_id` stays whatever was passed in
(no new case is created from that turn, and the secret is never persisted
anywhere — not the database, not Cognee, not logs).

## Proactive attention (fintech shell)

- `GET /api/nishchint/attention?customer_id=` — `{"has_attention": bool, "items": [...]}`.
  Computed fresh every call from open cases + Bills/FASTag/AutoPay/Refunds
  mismatches (`AttentionService`) — never a stored/cached list, so it can't
  go stale or duplicate. Powers the home dashboard's "Nishchint is watching
  N things for you" panel.

## Bills / FASTag / AutoPay / Refunds

Lighter mock domains (spec sections 16-19) — each has its own deterministic
"insight" computed server-side from two already-verified fields (never
routed through the T+1/T+5 policy engine, which is specific to UPI failed
payments):

- `GET /api/customers/{customer_id}/bills`, `GET /api/bills/{bill_id}`,
  `POST /api/bills/{bill_id}/investigate` — opens/reuses a lightweight case
  (`intent=BILL_RECONCILIATION`, no `transaction_id`).
- `GET /api/customers/{customer_id}/fastag`,
  `POST /api/fastag/{account_id}/investigate` — same pattern, `intent=FASTAG_BALANCE_MISMATCH`.
- `GET /api/customers/{customer_id}/autopay`,
  `POST /api/autopay/{mandate_id}/review`,
  `POST /api/autopay/{mandate_id}/cancel` — cancel mutates mock mandate
  state and writes an audit event; never claims to touch a real bank mandate.
- `GET /api/customers/{customer_id}/refunds`, `GET /api/refunds/{refund_id}`,
  `POST /api/refunds/{refund_id}/investigate` — `intent=REFUND_MISMATCH`.

Cases created by these `investigate` endpoints are idempotent per
`(customer_id, intent)` (via `CaseService.get_open_case_for_intent`, used
inside `get_or_create_case` whenever no `transaction_id` is given) and show
up in `GET /api/cases` / the customer Case Center / operations
dashboard exactly like a failed-payment case, minus `policy_result` (which
stays `null` — there's no T+1/T+5 deadline for a bill/FASTag/refund issue).

## Customers

- `GET /api/customers/{customer_id}` — basic profile.
- `GET /api/customers/{customer_id}/context` — customer + recent
  transactions + open cases + recent messages (`MemoryService`).
- `GET /api/customers/{customer_id}/notifications` — in-app notification
  feed.

## Transactions (mock Paytm layer)

- `GET /api/transactions/{transaction_id}`
- `GET /api/customers/{customer_id}/transactions`

## Cases

- `GET /api/cases?status=&priority=&customer_id=` — list. Used by the
  operations dashboard (no filter) and the customer-facing Case Center
  (`customer_id`). Each row includes `transaction_id` (the transaction
  detail page uses this to find an existing case for a transaction) and
  `closed_at` (used for the operations dashboard's average-resolution-time
  metric).
- `GET /api/cases/{case_id}` — full case detail: customer, transaction,
  live policy evaluation, messages, audit-log-derived timeline, active
  follow-up, dispute, and a `memory` section:
  `{"cognee_configured": bool, "previous_interactions": [{"text","source"}],
  "related_incidents": [{"text","source"}]}` — best-effort semantic memory
  for this case's customer and (if the transaction has a merchant) related
  merchant incidents. Empty arrays, never an error, when Cognee isn't
  configured or a lookup fails.
- `GET /api/cases/{case_id}/summary` — an LLM-written (or template
  fallback) human-readable summary for the operations dashboard.
- `POST /api/cases/{case_id}/override` — human-in-the-loop action.
  `{"action": "APPROVE" | "OVERRIDE", "new_status": "...", "note": "...", "operator": "..."}`.
  `APPROVE` defaults to `WAITING_FOR_RESOLUTION`; `OVERRIDE` requires an
  explicit `new_status`. Invalid transitions return `409`. Always writes a
  `HUMAN_OVERRIDE` audit event.

## Tickets

- `POST /api/tickets` — `{"customer_id", "transaction_id", "intent"}`.
  Idempotent: reuses an already-open case for the same transaction.
- `GET /api/tickets/{ticket_id}`

## Disputes

- `POST /api/disputes` — `{"case_id", "transaction_id", "reason"}`.
  Compensation is computed server-side from the rules engine, never from
  the request body. Idempotent per case.
- `GET /api/disputes/{dispute_id}`

## Follow-ups

- `POST /api/followups` — `{"case_id", "scheduled_for"}`. Idempotent per
  case (returns the existing active follow-up instead of duplicating).
- `GET /api/followups/{followup_id}`

## n8n workflow integration

- `POST /api/workflows/execute-followup` — `{"followup_id"}`. Runs the
  recheck → policy → decide → act loop. Called by the n8n "Wait" node once
  a follow-up is due, and by the simulated-clock endpoints as a fallback
  when n8n isn't configured. Idempotent (no-ops if already `COMPLETED`).
- `POST /api/workflows/followup-result` — the spec's n8n callback contract.
  Requires `"secret"` to match `N8N_CALLBACK_SECRET`. `401` on mismatch.

## Simulation (demo clock)

- `POST /api/simulate/advance-time` — `{"days": 1, "hours": 0}`. Advances
  the simulated clock and executes any follow-ups now due.
- `POST /api/simulate/advance-to-deadline` — jumps straight to the next
  scheduled follow-up's `scheduled_for` and executes it.
- `GET /api/simulate/current-time`
- `POST /api/simulate/reset` — wipes all demo data and reseeds the fixed
  customers/transactions from `app/database/seed.py`, resets the clock to
  the demo start time. This does NOT touch Cognee memory by design — see
  "Cognee scripts" below.

## Voice input

- `POST /api/voice/transcribe` — multipart form upload, field `file` (audio
  blob, any format ffmpeg/faster-whisper can decode — the frontend sends
  webm/opus from `MediaRecorder`). Returns
  `{"text": "...", "language": "hi", "language_probability": 0.97}`.
  Local `faster-whisper` model, auto-detects language — never assumes
  Hindi or English. `400` on an empty file, `503` if the model fails to
  load/run (e.g. first-use model download still in progress); the
  frontend falls back to typed input either way, nothing else in the app
  is affected. The transcribed `text` is just handed to `POST /chat` like
  any typed message — no separate voice-specific understanding path.

## Cognee scripts (not HTTP endpoints)

There is deliberately no API endpoint to write/reset Cognee memory — spec
section 31 asks that a destructive memory operation never be part of the
normal API/UI. These are run manually from `backend/`:

- `python -m scripts.test_cognee` — verifies real Cognee Cloud credentials
  work end to end (write + retrieve). Exits non-zero with a clear message
  if `COGNEE_API_KEY`/`COGNEE_BASE_URL` aren't set.
- `python -m scripts.seed_cognee` — seeds Priya's historical case memory
  (and a couple of synthetic Apollo Medicals incidents for other customers)
  so the "related incidents" and contextual-follow-up demo have something
  to retrieve without needing a prior live conversation.
- `python -m scripts.reset_cognee_demo --yes` — deletes only the
  `COGNEE_DATASET` dataset (default `nishchint_memory`), nothing else in
  the Cognee Cloud account.

## Errors

The backend never lets an unhandled agent/tool exception surface as a raw
500 from `/chat` — it's caught, logged server-side, and returns a safe
"I've kept your case open and routed it for review" response instead (spec
section 43). Everything else returns standard FastAPI validation/HTTP
errors (404 for unknown IDs, 409 for invalid case transitions, 401 for a bad
n8n callback secret).
